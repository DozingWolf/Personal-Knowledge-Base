# 01 总体方向与架构选型

> 起点问题：能否用「本体论」这一方法论，逐步构建一个跨领域（国际关系 / 信息技术 / 医疗供应链 / 人力资源）的知识库网络？还需要哪些组件？是否要 Neo4j 这类图数据库？

## 1. 概念澄清（术语第一次出现即解释）

| 术语 | 含义 |
|---|---|
| **本体 / Ontology（知识工程）** | Gruber 1993 定义：对某个概念化过程的**显式规范**。落到工程上即：为一个领域定义**概念（类）、属性、关系、约束**。管的是「模式层」，不是「数据层」。 |
| **本体论（哲学）** | 研究「存在什么」。与工程意义的「本体」不是一回事。 |
| **T-Box（术语层）** | 类型定义，如「人」「组织」「任职事件」及其允许的关系。 |
| **A-Box（断言层）** | 具体实例数据，如「张三 任职于 某公司」。 |
| **三元组（Triple）** | 主语—谓语—宾语 的最小事实单位，RDF 数据模型的基础。 |
| **实体消解 / Entity Resolution** | 判断多个指称是否指向同一实体（IBM = 国际商业机器公司）。整条流水线最脏、最贵的一环。 |
| **RAG（Retrieval-Augmented Generation，检索增强生成）** | 先检索材料再让大模型基于材料生成答案，抑制幻觉与知识过期。 |
| **GraphRAG** | 微软 2024 年提出：用 LLM 从语料抽实体与关系建图，再做**社群检测（Community Detection）**生成分层摘要，检索时兼顾局部邻居与全局主题。 |
| **属性图 / Property Graph** | 节点与边可挂任意键值对与标签，查询用 **Cypher**（Neo4j 的声明式图查询语言）。 |
| **RDF / OWL / SPARQL** | W3C 语义网三件套：RDF（Resource Description Framework，资源描述框架，数据模型）、OWL（Web Ontology Language，网络本体语言）、SPARQL（查询语言）。推理强但工程重、对 LLM 不友好。 |
| **双时态建模 / Bi-temporal Modeling** | **Valid Time**（事实在现实世界的有效期）与 **Transaction Time**（我们何时知道它）分开存储。 |
| **再化 / Reification** | 把一条关系提升为一个独立对象，使关系本身可以带属性。 |
| **派生属性 / Derived Property** | 由代码实时算出的虚拟字段（Palantir 概念）。 |
| **能力问题 / Competency Questions** | 本体工程的标准起点方法（Grüninger & Fox, 1995）：**先写下真正想回答的问题，再倒推需要哪些类型与关系**。 |
| **SKOS** | Simple Knowledge Organization System，受控词表的轻量标准。 |
| **上层本体 / Upper Ontology** | 跨领域共享的基础概念层，如 **BFO**（Basic Formal Ontology）、**DOLCE**。 |

## 2. 关键区分：Palantir 的本体论 ≠ 学术本体论

Palantir Foundry / AIP 的 Ontology **不遵循 OWL/RDF**，而是一个**以对象为中心的语义层 + 操作层**。Palantir 自己拆为三部分：

- **Semantics（语义）**：**Object Type（对象类型）**、**Object（实例，有主键/属性/链接）**、**Property（属性，可为派生属性）**、**Link Type（链接类型）**。
- **Kinetics（动力）**：**Action Type（动作类型）**——定义可对对象执行的写操作（批准、派遣、作废），带参数、校验、副作用、审批流、权限。**这是与普通知识库最大的分野**：它不是静态资料库，而是能改变现实世界状态的系统。
- **Dynamics（动态）**：数据源实时接入，本体随业务演化。

**重要判断：Palantir 的本体论是一层抽象，不是一种存储技术**（其底层并非图数据库）。

### 值得借鉴的四点（而非画一张实体关系图）

1. **派生属性**——对象上有些面是算出来的，不是存进去的。
2. **动作**——把「确认实体合并」「标记关系存疑」「调整可信度」做成显式操作，而非随意改数据。
3. **时间旅行 / as-of query**——「2024 年 3 月时我们认为什么」。
4. **权限绑定到对象属性**。

## 3. 通用组件清单（10 层，标注可否后补）

| # | 组件 | 说明 | 优先级 |
|---|---|---|---|
| 1 | **原始层 / Source Layer** | 原始文档不可变，带元数据（来源/时间/作者/可信度）。换模型或改本体时需要重跑抽取。 | 必需 |
| 2 | **本体层 / Schema** | YAML/JSON 定义类、属性、关系、约束，进版本控制。每个类型写**定义 + 正例 + 反例**，同时充当 LLM 抽取提示词。 | 必需 |
| 3 | **抽取层 / Extraction** | LLM 结构化输出（Structured Output / Function Calling）转成候选实体与关系。先抽实体 → 消解 → 再抽关系（用规范 ID）。**每条断言强制附带原文位置（span）**。 | 必需 |
| 4 | **消解与合并层** | 字符串相似 → 阻塞分桶（Blocking，把候选对降到 O(n)）→ 向量相似 → 图结构相似 → LLM 仲裁 → 人工确认。 | 必需（最耗时） |
| 5 | **变更管理 / 增量更新层** | **断言（Assertion）为一等公民**：`(主体, 关系, 客体, 来源, 生效时间, 记录时间, 可信度, 状态)`。含证据链、双时态、矛盾检测。 | 必需 |
| 6 | **存储层** | 图库 + 向量库 + 文档库。 | 需要，选型不急 |
| 7 | **推理与分析层** | 结构化查询（Cypher/SPARQL）、图算法、规则推理。 | 回报最高 |
| 8 | **检索 + Agent 层** | 混合检索（向量 + 图遍历 + 全文 + SQL），把查询与动作封装为工具给 LLM。 | 需要 |
| 9 | **人在环与治理层** | 审核队列、合并确认、权限分级、审计日志。 | HR 类数据必需 |
| 10 | **界面层** | 图可视化（Neo4j Bloom、Gephi、Cytoscape）；个人场景可用 Obsidian / Logseq。**注意**：Obsidian 的图是文档级链接图，本体要的是实体级关系图，粒度不同。 | 别低估 |

## 4. 图数据库选型

| 类型 | 选项 | 备注 |
|---|---|---|
| 嵌入式（无服务） | Kùzu、DuckDB + 扩展 | 像 SQLite 之于图，pip 装最省事；**留意其维护状态** |
| 本地服务 | Neo4j Community、Memgraph | 需 JVM 或 Docker |
| 云托管 | Neo4j Aura Free、Amazon Neptune | Aura 有免费层，零安装 |
| 一套打通 | PostgreSQL + pgvector + Apache AGE | AGE 是 Postgres 的图扩展，支持 openCypher |
| 纯 RDF | Oxigraph、Apache Jena、GraphDB | Oxigraph 有 Python binding |

**本机环境约束**：无 Docker、无 node，python3 可用。最顺路径为 **Neo4j Aura 免费实例**（零安装）或 **pip 装嵌入式图库**；本地跑 Neo4j 社区版需先装 JVM。

**选型原则**：业务数据（订单、价格、客户）天然是表格结构，关系型数据库够用。**用图的思维建模，但第一版可用关系型 + 一张显式的传导/关系边表起步**（本身就是图）。等要跑「任意路径探索」「网络中心性」时再叠加图库，迁移成本低。**不要为图数据库而扭曲业务数据模型。**

## 5. 六个容易踩的坑

1. **别从本体开始，从问题开始。** 先写能力问题，再倒推类型与关系。最常见的失败是设计三个月本体，然后发现没有查询想跑。
2. **本体要长出来，不要设计出来。** 让 LLM 定期读图并提建议（该合并、该拆分），但每次变更过人工审核。
3. **幻觉边会沿图传播。** 错误连接会被后续推理放大。没有证据链 + 抽样评测，图会退化。必须做**评测**（抽样人工标注，算抽取精确率/召回率）。
4. **多领域要有上层本体。** 共享概念（人、组织、事件、地点、政策、时间）放公共层，各领域做扩展。
5. **HR 类数据性质特殊**：高频变更、强时效、强合规（敏感数据分级、访问审计），架构上提前留口。
6. **三段式分工要清楚**：LLM 负责「把非结构化变成结构化」，**图算法负责「从结构里发现模式」**，LLM 再负责「把模式翻译成人话」。不要指望 LLM 同时干三件事。
