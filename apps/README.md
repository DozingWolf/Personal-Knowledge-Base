# apps/ — 面向岗位的应用

> `core/` 提供能力，`domains/` 提供领域知识，`apps/` 把两者组装成**某个岗位每天会打开的东西**。

## 一、规划中的应用

| 应用 | 面向谁 | 解决什么 | 依赖 | 阶段 |
|---|---|---|---|---|
| 政策预警 | 商务 / 产品负责人 | 政策或价格变化后，**第一时间知道哪些品类与产品受影响** | M12 影响图 + M14 预警 + M15 输出 | 一期后段 |
| 组合健康度诊断 | 总经理 / 商务负责人 | 现有代理组合的**暴露度、分散度、风口判断**，输出增配/维持/减配/找替代 | M9 映射 + M13 评分 | 一期后段 |
| 专家审核台 | 产品 / 商务专家 | SKU ↔ 检测项目的**一屏决策**（本项目的关键生产力工具） | M10 审核工作台 | **V1 纵切** |
| 情景推演 | 决策层 | "某政策落地，我司营收/毛利影响区间" | 需第二阶段的内部数据 | 三期 |

## 二、形态未定项（待用户决策）

- 交付形态：**静态报告 / 交互看板 / 问答式**——先做哪个决定 M13 的产出结构（见 [discuss/06](../discuss/06-功能模块设计.md) 第九节）。
- 专家审核台是**内部工具**（可忍受朴素），还是需要正式 UI 框架——取决于专家人数与使用频次。

## 三、约束

1. 应用**不含领域知识**：领域差异从 `domains/` 读，应用只负责"组装 + 呈现 + 交互"。
2. 应用**不直接读上游模块的内部表**，只消费已发布数据集（含 `as-of` 与证据）。
3. 面向人的界面**必须用业务语言**：政策术语需经 `terminology.yaml` 翻译（如"联检折扣"→"多指标一起做的折扣"）。
