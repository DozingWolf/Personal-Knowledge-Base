# ADR 0001：采用「平台内核 / 领域包 / 应用」三层架构 + 注册表接入

- **状态**：已采纳
- **日期**：2026-10-06
- **相关**：[discuss/07](../../discuss/07-平台化预留与渐进明细.md)、[discuss/06](../../discuss/06-功能模块设计.md)

## 背景

产品当前定义在 **IVD（体外诊断）试剂贸易**领域，但明确要求未来能形成**可复用、可扩展的方法论与业务基础框架**。

设想中的复用路径（用户给出）：

1. 第一个领域：IVD 试剂贸易（当前）
2. 第二个领域：**体外诊断试剂供应链管理**（同域延伸）
3. 第三个领域：**国际关系 / 国际舆情 / 贵金属关联分析**（跨域跳跃）

约束：
- 目前只有**一个**真实领域实例，无第二实例可用于验证抽象；
- 团队规模小，交付速度敏感；
- 已积累的领域资产（662 个检测项目、3825 条编码映射、两份政策分析）不应因架构调整而重做。

## 决策

采用**三层结构**，并以**注册表（registry）**作为领域包接入内核的唯一方式：

```mermaid
flowchart LR
  K["平台内核 core/<br/>领域无关"] --> A["应用 apps/"]
  P["领域包 domains/<domain>/<br/>只声明，不改内核"] -->|"注册表"| K
  P -.-> A
```

1. **内核**承载领域无关能力：采集框架、证据链、本体引擎、消解、映射框架、人审工作台、影响图引擎、治理审计。
2. **领域包**只声明：本体扩展、编码体系、词典、层级模板、评分卡、价格规则集、术语字典。
3. **硬约束**：领域包**不得修改内核代码**；`domains/` 之外不得出现领域专有字面量（可 `grep` 检查）。

## 理由

1. **"隔离"是低成本且确定有益的，"抽象"是高成本且需要证据的。** 现在做隔离，代码立即受益（可读、可测、可讲）；现在做抽象，没有验证对象，大概率抽象错。
2. **注册表是本方案的最小侵入点**：领域差异集中在少数配置文件里，内核只认注册表的形状，不认 IVD 的概念。
3. **复用路径给了一个强信号**：第二、三个领域的差异主要在"**主体与关系**"（组织、角色、供需、事件与传导），说明内核中**影响图引擎与主体关系建模**是真正可复用的部分，而"证照/注册证"这类只属 IVD。
4. 与既有设计不冲突：01 的"10 层通用组件"、02 的"六层传导栈"、06 的 17 个模块，只是被重新划归到内核与领域包两侧，无一废弃。

## 后果

**正面**
- 第二个领域到来时，理想情况是"新增一个 `domains/<x>/` + 改配置"，不改内核。
- 领域资产（词典、本体扩展、评分卡）成为**可复用资产**而非一次性代码。
- 强制边界使"哪个改动该放哪里"不再需要逐次讨论。

**代价（诚实记录）**
- 需要维护注册表的 schema，并忍受"为了填注册表而多写一层"的前期成本。
- 领域包与内核的边界会有**判断模糊地带**（如"产品/组织"这类半通用对象），需逐案决定，可能反复。
- 隔离纪律靠人守时容易破；必须辅以机械检查（grep 守则）。

## 被否决的替代方案

| 方案 | 为什么没选 |
|---|---|
| **现在就建插件协议 / 动态加载** | 只有一个领域，协议无验证对象；会拖慢交付并锁死错误抽象 |
| **单体不分区，等需要时再拆** | 领域语义会渗进内核，重构成本随代码量指数上升；隔离现在几乎免费 |
| **直接微服务化** | 单进程 + 模块边界已足够；多租户/独立部署尚无需求 |
| **为"第二、三领域"预建能力** | 第三领域（国际关系/舆情/贵金属）形态差异大，预建必错；应按台阶 2 按需演进 |
| **不留决策日志，只留结论** | 第二个领域只能抄表结构、抄不到判断；复用价值大打折扣 |
